# PRI Website

## What this is

The public website and backend platform for **PRI** (Policy and Research Initiative). It is the initiative's central digital platform: it showcases PRI's mission and research, hosts a public knowledge hub (publications, datasets, visual tools), supports outreach and donor communication, provides portals for fellows/interns/researchers, and runs operational workflows (event registration, job postings, program tracking).

Source spec: `12. Website Development.docx` (project root) — a two-part document covering the frontend site structure and the backend development plan. This CLAUDE.md is the working summary; the docx is the canonical original if anything here needs re-checking.

## Tech stack (fixed)

- **Frontend:** Next.js (this repo, `prikeralam/front-end`), deployed as a Docker image (standalone Next server) by GitHub Actions to one EC2 host per environment that it shares with the backend, in PRI's AWS account; nginx and certbot run on that host (see website-backend's `docs/deploy/aws-provisioning.md`)
- **Backend:** Django (repo `website-backend`); the frontend talks to it over the versioned REST contract in that repo's `docs/api/` (see "Backend integration" below)
- **API layer:** Django REST Framework only. The FastAPI hybrid that was once an open question was never adopted: `website-backend` is Django + DRF end to end.
- **Database:** PostgreSQL
- **File storage:** AWS S3 or DigitalOcean Spaces (datasets, publications, media)
- **Hosting:** VPS (DigitalOcean/AWS Lightsail) or Docker containers
- **Search:** ElasticSearch or Postgres full-text search (repository/publications/media-watch tagging)
- **Version control / CI:** GitHub (`prikeralam/front-end`, private) with GitHub Actions CI — see "Git workflow" below
- **Security baseline:** SSL, 2FA/OAuth on admin panels, rate limiting, encrypted backups

## Workflow rule

## Backend integration

How the frontend talks to `website-backend` (contract: that repo's `docs/api/`, `openapi.yaml`). Details and reasons are in the 2026-09-25 changelog entries.

- **Config:** `API_URL` (server-side only; see `.env.example`). Types are generated, not hand-written: `npm run api:types` rewrites `app/_lib/api/schema.d.ts` from the contract (override the source with `API_SCHEMA`). Run it whenever the backend changes an endpoint, and commit the result with the frontend change that needs it.
- **Public pages** (server components) read through `app/_lib/api/*`: a server-only typed client (cached for a minute, and expired at once by dashboard edits; see `_lib/api/publicCache.ts`), pure adapters that map API shapes onto the types in `_lib/types.ts` (so UI components did not change), and `load()` + `ApiMessage` (`LoadError`, `NotPublishedYet`) for explicit error and empty states. Never fall back to mock content.
- **Signed-in features** use the JWT flow behind `app/api/auth/[[...action]]`: tokens live only in httpOnly cookies; browser code asks `/api/auth/session` and mirrors `{id, name, email, role}` into `_lib/session.ts`, which components read with `useSession()` / `useRequireSession()`. Calls that need the user's token are **Server Actions** (`_lib/dashboard/*Actions.ts`, using `getAccessToken()`), which validate every argument and rely on the backend to enforce roles. Use `uncachedApi` / `backendRequest` for anything per-user, and for every write.
- **Image hosts are baked at build time.** `next.config.ts` is compiled into the Docker image and one image is promoted from staging to production, so media hosts for `next/image` come from the build-time `IMAGE_HOSTS` repository variable (both environments' buckets), not from the runtime `API_URL`.
- **Backend gaps that shape the UI** (raise with the backend, do not paper over): people, projects, documents and testimonials are addressed by id only (slugs are resolved from the cached list); no display names on content or audit rows (creators show as "user #9"; the list-users endpoint exists but is admin-only); no "my access requests" endpoint. Data story bodies are uploaded HTML files (see `docs/data-stories.md`); the four stories written before that keep their hand-built bodies.
- **Still mock:** the fellow profiles under `/fellowship` (`_content/fellows.ts`). Events, job openings and applications are real (phase 3, below); of G, only the contact form is real. Donations go through PRI's Razorpay payment page or a bank transfer to PRI's HDFC account (both real). The dashboard's favorites, download history, API keys and watched themes screens were removed rather than faked (#15); bring each back when the backend adds an endpoint. The users screen came back on the real API (#42).
- **Accounts** (backend Module H): admins manage users at `/dashboard/users` through `_lib/dashboard/userActions.ts`; access is per role, so "giving access" is changing the role. Invite and reset emails link to `/reset-password` (the backend's `FRONTEND_URL` must be this site's origin). The session reads `/users/me/`, whose `must_change_password` makes the dashboard layout ask for a new password before anything else.

## Git workflow

Same as the backend repo (`website-backend`); full description in `.github/CONTRIBUTING.md`.

- Branches: `feat/<issue#>-<desc>` (or `fix/`, `chore/`, `refactor/`, `docs/`) -> `dev` -> `staging` -> `main`. Never commit or push directly to `dev`, `staging` or `main`; a push to `staging` deploys to the staging EC2 host, and a push to `main` deploys to production after manual approval (`deploy-staging.yml`, `deploy-production.yml`).
- Merge methods: squash work branches into `dev`; **merge commits** for promotions (`dev` -> `staging`, `staging` -> `main`). Hotfixes: `fix/*` from `main` into `main`, then merge the two auto-opened `backport/*` PRs.
- Commits: Conventional Commits, `<type>(<scope>): <summary>`. **No `Co-Authored-By` trailer.** PR bodies end with `Closes #<issue>`; use `.github/PULL_REQUEST_TEMPLATE.md`.
- CI (`.github/workflows/ci.yml`): `lint`, `typecheck`, `test`, `build` and `docker-build`, all blocking; `pr-guard.yml` enforces the branch flow. Branch rulesets need GitHub Pro/Team on a private repo, so until applied the flow is followed by convention: merge only when checks are green. `scripts/setup-github-protection.sh` applies rulesets, labels and the `staging`/`production` Environments.
- After a backend contract change, run `npm run api:types` and commit the regenerated `app/_lib/api/schema.d.ts` with the frontend change that needs it.
